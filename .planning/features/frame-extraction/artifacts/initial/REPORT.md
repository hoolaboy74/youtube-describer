## 검증

- 원본: 7Nqb1X25WJk, 360p format 18, 24,663,712바이트, 1,260.983초.
- 모든 실제 영상 실행에서 기존과 동일한 수의 키프레임·보충 프레임을 얻었습니다.
- 21분 영상: 242 키프레임 + 725 보충 = 967장. QA 저장 포함 실행에서는 967장 모두 임시 DB에 등록됐습니다.
- 21분 영상의 최대 프레임 간격: 현재와 최초 묶음 모두 1,533ms.
- 빈 구간, 범위 밖 시각, 중복 PTS, 추출 실패 없음.
- 최초 묶음 방식: 키프레임 242장 모두 원본 시각과 이미지 SHA-256 일치.
- 보충 725장 중 686장의 PTS가 정확히 일치하고 709장의 이미지 SHA-256이 일치했습니다.
- 따라서 전체 967장 중 PTS 일치 928장, 이미지 일치 951장입니다. 차이가 있는 PTS는 최대 33ms(30fps 한 프레임)입니다.
- 이는 개별 seek와 순차 decode의 프레임 선택 경계가 완전히 같지 않음을 뜻합니다. 동일 이미지·동일 타임스탬프를 모든 프레임에서 보장하는 구현은 아닙니다.

## 방식

운영 frameExtraction.js를 읽어서 현재 방식으로 실행했습니다. 비교용 모듈은 메모리에서 보충 루프만 교체했습니다. FFprobe, 최초 키프레임 선택, showinfo PTS 수집, JPEG decode 검증, checksum, coverage 검증은 기존 코드를 사용했습니다.

기존 방식은 보충 시각마다 FFmpeg를 실행하고 최대 2개씩 병렬 처리합니다. 묶음 방식은 보충 시각을 정렬한 뒤 한 번의 순차 디코딩에서 각 시각 이후 첫 프레임을 선택합니다. FFmpeg select 식에서 다음 목표 시각을 균형 트리로 조회해 긴 목표 목록의 매 프레임 탐색 비용을 줄였습니다.

QA 저장 비교에는 운영 createQaCacheManager 및 better-sqlite3를 사용하되 DB와 이미지 경로를 임시 디렉토리로 분리했습니다. 운영 DB와 캐시는 수정하지 않았습니다. 다운로드, 자막, Whisper, Gemini, 영상 생성 경로 전체는 측정에 포함하지 않았습니다.

nice 10 및 ionice best-effort 7로 순차 실행했습니다. 기본 리소스 제한(ffmpeg 3, backfill 2)을 그대로 사용했습니다. /usr/bin/time이 설치되어 있지 않아 Python 자식 프로세스 rusage 차이로 CPU 시간을 측정했습니다. maxrss는 이전 실행의 최고값을 포함할 수 있어 메모리 비교 근거로 사용하지 않았습니다.

## 추가 경계 실험과 대조군

밀리초 반올림을 고려해 목표 비교에 0.5ms 허용을 넣은 별도 변형도 측정했습니다. 시간은 20.52초(캐시 제외), 27.01초(캐시 포함)로 비슷했습니다. 그러나 원본 PTS 및 checksum 일치가 각각 898/967장으로 줄었고 차이 상한은 여전히 33ms였습니다. 경계 허용만으로 개별 seek의 선택을 동일하게 재현할 수는 없었습니다. 최초 묶음 방식보다 동일 프레임 재현성이 좋아진 결과가 아니므로 추가 최적화로 권하지 않습니다.

같은 영상의 첫 60초를 키프레임 2초 간격으로 다시 인코딩한 통제 대조군도 실행했습니다. 이는 실제 다운로드된 유튜브 포맷의 키프레임 간격을 나타내는 자료가 아닙니다. 현재 방식 0.525초, 묶음 변형 0.519초; 양쪽 키프레임 30장, 보충 0장, PTS 및 checksum 전부 동일했습니다. 보충이 필요 없을 때 묶음 디코딩을 실행하지 않는 분기가 작동했습니다.

## 판단과 한계

이 영상에서 가장 큰 개선 대상은 보충 프레임의 개별 FFmpeg 실행입니다. QA 캐시 저장은 6~8초 정도의 추가 대기여서 주병목으로 보기 어렵습니다. 수백 장 보충에는 묶음 추출을 우선 적용하고, 실제 원본 시각·범위·중복·coverage 검증을 유지하는 방향이 적절합니다.

실제 원본은 한 영상이고 짧은 구간도 같은 원본에서 가져왔습니다. 주요 조건마다 1회 측정이며 여러 영상에서의 평균이나 p95 성능은 아닙니다. 영상 해상도, 코덱, VFR, 길이, 실제 동시 부하에 따라 차이가 있습니다. 전체 디코딩이 필요한 묶음 방식은 보충이 적은 영상에서 손해일 수 있어 개별 seek와 묶음 방식의 전환 기준을 별도로 측정해야 합니다. 기존과 동일한 원본 프레임 선택이 필수라면 33ms 경계 차이에 대한 계약도 결정해야 합니다.

운영 코드 변경·배포·서비스 재시작은 하지 않았습니다. 원본, 스크립트, 원시 결과 JSON, 이미지와 임시 DB는 원격 임시 디렉토리에 보존했습니다(약 258MB).
