## 판단

소량 보충에는 키프레임과 개별 seek가 유리합니다. 보충이 많으면 한 번의 전체 디코딩에서 실제 2초 간격 프레임과 원본 키프레임을 함께 뽑는 방식이 빠르고 시각 근거도 정확했습니다. 빠른 key-only 경로에는 원래 PTS와 FFmpeg 보정 시각이 일치하는지 검사하고, 불일치나 비정상 순서가 있으면 전체 디코딩으로 전환하는 조건이 필요합니다.

QA 저장, 운영 DB, 캐시, TTS, Whisper, Gemini는 테스트하지 않았습니다. 다운로드 시간도 추출 측정에서 제외했습니다.

## 원본 시각과 이미지 대조

독립된 전체 디코딩에서 정수 PTS와 stream time_base를 읽고 JPEG SHA-256을 비교했습니다. showinfo 문자열 정밀도를 고려해 검색에는 5ms를 허용했지만 검증된 새 방식의 실제 최대 시각 오차는 모두 0ms였습니다. 같은 이미지가 반복됐다는 이유로 실패시키지 않고 그 시각의 실제 원본과 비교했습니다.

미검증 항목에는 해당 PTS의 실제 프레임을 찾지 못한 경우와 그 시각의 원본 이미지가 다른 경우가 포함됩니다. 모든 미검증 항목이 같은 크기의 오류라는 뜻은 아닙니다. 새 한 번 처리 방식은 모든 실제 영상과 통제군에서 이미지, 시각, 범위, 중복 PTS, 약 2초 coverage를 통과했습니다. 3회 반복의 시각과 이미지도 일치했습니다.

## 현재 key-only 경로에서 발견한 시각 오류

뮤직비디오에서 현재 이미지의 기록 시각은 26.485초였지만 같은 JPEG의 실제 원래 표시 시각은 23.023초였습니다. FFprobe key-only 출력도 같은 프레임에 pts_time=23.023000, best_effort_timestamp_time=26.484792를 보여 줬습니다. 일부 출력 순서도 원래 PTS 순서와 달랐습니다. showinfo의 보정 시각만으로 원본 시각을 판단하면 잘못 연결될 수 있습니다.

이 문제는 오케스트라와 뮤직비디오에서 관측했습니다. 스레드 1개 제한과 +igndts 탐색으로 없어지지 않았습니다. FFmpeg 전체 버전의 일반적인 원인을 단정하지 않고, 설치된 FFmpeg 7.1.1과 이 입력들의 관측 결과로 기록합니다.

원래 pts를 key-only JPEG 순서와 연결하는 수정 탐색은 뮤직비디오에서 164/164 원본 대조를 통과했지만 7.07초로 한 번 처리 4.24초보다 느렸습니다. 1회·한 입력의 탐색이며 다른 입력 검증을 끝낸 배포안은 아닙니다.

기존 PTS와 새 PTS만 비교하면 기존의 잘못된 시각 때문에 키프레임을 잃은 것처럼 보일 수 있습니다. 초기 retention 수치 대신 최종 원본 packet PTS와 전체 디코딩 대조로 보존을 검증했고, 새 방식은 선별한 원본 키프레임을 전부 포함했습니다.

## 소량 보충 전환 시험

같은 원본에서 만든 10분 통제 영상입니다. 대부분 2초 간격 키프레임을 넣고 일부 구간만 6초 간격으로 만들어 보충 수를 조절했습니다. 실제 유튜브 GOP 분포를 대표하지 않는 재인코딩·반복 영상입니다. 각 3회 중앙값입니다.

| 보충 수 | 개별 seek | 묶음 보충 | 한 번 처리 하이브리드 |
|---|---:|---:|---:|
| 3 | 3.86초 | 8.78초 | 7.29초 |
| 12 | 4.50초 | 9.02초 | 7.38초 |
| 60 | 8.64초 | 8.74초 | 7.33초 |
| 180 | 18.54초 | 8.74초 | 7.25초 |

3장과 12장은 개별 seek, 60장과 180장은 한 번 전체 처리가 유리했습니다. 이 10분 통제 입력의 전환점은 12~60장 사이입니다. 모든 코덱·해상도·길이에 고정 숫자로 적용할 근거는 아닙니다.

픽셀 디코딩 없이 packet flags와 PTS만 읽는 사전 계획 검사는 약 0.15~0.68초였습니다. 이 시간은 성능 표에 포함하지 않았습니다. 시각이 정상인 7개 입력에서 예상 키프레임과 보충 수가 실제 결과와 일치했습니다. 비정상 시각 입력 둘에서는 기존 결과의 개수도 원본 packet 기준과 달랐습니다.

## 추천 흐름

1. 원본 packet 키프레임 PTS로 예상 보충 수와 영상 길이를 파악합니다.
2. 보충이 적으면 key-only decoder의 원래 pts와 best_effort 시각 및 출력 순서를 검사합니다. 정상이라면 키프레임+개별 보충을 사용합니다.
3. 보충이 많거나 시각 검사가 실패하면, 한 번 전체 디코딩하면서 실제 2초 격자 프레임과 최소 1초 간격 원본 키프레임을 함께 출력합니다.
4. 원본 PTS, 시작·끝 coverage, 범위, 중복, JPEG 검증을 유지합니다. 복제 프레임의 가상 fps 시각을 원본 시각으로 사용하지 않습니다.
5. 전환 기준은 영상 길이와 예상 seek 비용/전체 decode 비용을 비교합니다. 이번 10분 시험은 12장까지 개별, 60장 이상 한 번 처리가 유리함을 확인했고 중간 경계는 확정하지 않았습니다.

네 실제 영상 모두 한 번 처리 하이브리드가 두 pass 방식보다 빨랐습니다. 원본 메타데이터로 먼저 판단하면 불필요한 키프레임 JPEG pass를 피할 수 있습니다.

## 재현과 한계

worker.js, run.py, controls.py, hybrid.py, verify.js, final-checks.py 및 원시 JSON을 보존했습니다. worker는 운영 모듈을 메모리에서 수정해 시험하며 실제 운영 파일을 수정하지 않습니다.

실제 원본은 네 영상이고 주요 조건은 각 3회입니다. 360p 다운로드 조건에서 시험했으며 다른 코덱·해상도·VFR·장시간 입력이나 재시작/복구 검증은 아닙니다. nice 10, ionice best-effort 7로 실행했습니다. 운영 코드·DB·캐시 변경, 배포, 서비스 재시작은 하지 않았습니다. 원본과 결과는 원격 임시 디렉토리에 보존했습니다.
