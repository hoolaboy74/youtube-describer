# 영상 파일 입력 비교 — 가족 관찰 영상

## 실행

```bash
cd test_scripts
node compare_model_video.js -m gemini-3.8-flash -v lnUHSWhQ-UI -p ./prompt_template_video_v13.txt
```

기존 -m/-v/-p/-a/-h 파서·모델 목록 검증·asset 캐시를 공유한다. 단, 이 스크립트는 Gemini만 허용하며 OpenAI 지정은 미디어 처리 전에 거부한다. -a는 기존 공통 목록을 표시한다. -p는 현재 경로 기준, 미지정 시 기존 PROMPT_FILE 규칙을 따른다. 영상 입력용 프롬프트를 사용해야 한다.

새 영상에 대해서는 공통 준비 파이프라인이 프레임도 추출할 수 있지만, 모델에는 JPEG를 보내지 않고 원음이 포함된 MP4 파일만 보낸다. 이번에는 기존 캐시를 사용하여 다운로드·추출을 다시 하지 않았다. 제목·VTT는 기존과 같다. 동일 실행에서 여러 Gemini 모델을 선택하면 업로드 파일을 공유한다.

파일은 임시로 Files API에 업로드하고 ACTIVE를 기다린다. 완료/오류 후 이 실행이 만든 원격 파일만 삭제한다. 로컬 asset은 삭제하지 않는다. 업로드마다 파일 크기(최대 2GiB)와 SHA256·원격 정보·업로드/처리시간을 video_input.json에 기록한다. 정책·영상 파일의 실제 길이와 누적 초 규칙을 결합한 최종 요청은 MODEL.video-prompt.txt에 저장한다. 기본 처리 설정은 정적 1fps, MEDIA_RESOLUTION_LOW, temperature 0.7. agentic 모드는 아니다.

생성 원본과 result.json은 result/VIDEO_ID/video-XXXXXX에 저장한다. 원문은 자동 시간 보정·태그 정규화 없이 보존하며 DB·플레이어에 게시하지 않는다. input_context.frames와 result.frameCount는 기존 공통 준비 캐시의 프레임 수일 뿐 전송 이미지 수가 아니다. input_context.sampledFramesSent=false 및 modelInput=video_file_with_audio로 구분한다.

## 입력 및 비교 조건

- 원본 캐시 MP4: 22,256,871바이트, 640×320, 약 23.976fps, 629.563초, 오디오 스트림 포함. YouTube 메타데이터 길이는 630초.
- 모델: gemini-3.8-flash.
- 집필 프롬프트: v13에서 정지 이미지/타임스탬프 설명을 영상·원음에 맞게 수정한 prompt_template_video_v13.txt. 목표·장르·안전·직접 txt 규칙은 유지.
- 영상 제공과 오디오 제공뿐 아니라 샘플링 방식과 시간 지시도 바뀌었다. 개별 효과를 분리한 실험은 아니다.
- 공식 사용 방법: https://ai.google.dev/gemini-api/docs/generate-content/video-understanding

| 방식 | 디렉토리 | 항목 / txt | API 생성 초 | 입력 토큰 |
|---|---|---:|---:|---:|
| 기존 프레임 v13 | run-U7ZxAx | 28 / 9 | 20.959 | 109,654 |
| 영상 첫 실행 | video-aZCrbm | 31 / 4 | 20.150 | 78,019 |
| 영상 시간 규칙 강화 | video-gspTkC | 31 / 3 | 17.217 | 78,252 |

디렉토리 상위는 test_scripts/result/lnUHSWhQ-UI. 업로드+ACTIVE 대기는 각각 26.293초, 25.924초로 API 생성 시간에 별도 추가된다. 입력 토큰은 줄었지만 이를 USD 비용이나 품질 향상으로 동일시하지 않는다. 출력·추론 사용량은 각 result.json에 별도로 있다.

## 결과: 현재 설정은 채택하지 않음

첫 결과는 630초 영상에 [1000] 등을 출력했다. 분·초를 이어 쓴 것으로 의심되지만 이를 임의 변환하지 않았다. 31개 중 15개 시각이 범위 밖이며 기존 canonical 검사에서도 15개가 거부됐다.

두 번째는 실제 길이와 누적 초 변환 기준을 요청에 추가하여 전 시각이 범위 안에 들어왔다. 그러나 의미상의 정확도는 좋지 않았다.

- 61초: '숟가락을 입에 문 채 생각에 잠깁니다.' 실제 MP4 해당 시각에는 분홍색 어린이용 젓가락을 입 앞에 들고 있다. 물건 오인과 내면 추정.
- 411초: 남성이 냉동고 문을 연다고 하나 해당 MP4 화면은 천장과 진열대, 실패 여부를 묻는 편집 글자다.
- 426초: 초코 쭈쭈바 세 개를 꺼내 건넨다고 단정. 420~434초 구간을 1fps로 추가 추출하여 몇 장을 확인했으나 전달 동작/물건을 직접 확인하지 못했다. 전 프레임을 수동 감상한 것은 아니므로 실제 영상 어디에도 없다고 확정하지 않는다.
- 445초: 카드 결제 뒤 가방에 넣는다고 하나 실제 해당 프레임은 천장과 '자 여기 꽂아 주세요~' 발화 자막이다. 대사로 아는 과정을 보이는 행동처럼 표현하는 기존 문제가 반복된다.
- 499초: 비밀번호 누르기를 설명하지만 실제 해당 프레임은 유리문과 안내 문구이며 조작하는 손은 보이지 않는다.
- 필요한 436/442초 부근 편집 설명 등 기존에 전달하던 독립 글자가 많이 빠졌다. txt 총수만의 문제가 아니라 의미 있는 맥락 누락이다.

단일 호출에 원음을 추가했어도 이번에는 시각 근거/대사 구분이 안정적으로 좋아지지 않았다. 대본이 구체적이 된 부분을 자동으로 영상에서 새로 확인한 사실로 인정하지 않았다.

## 검사 및 주의점

25개 결정적 테스트 통과(공통 15, 검수 5, 영상 5). 영상 프롬프트는 4가지 원음 분류의 정책 로딩 검사 통과. 기존 스크립트의 단일 호출 동작은 유지했다.

두 번째 결과는 [4] [txt]처럼 두 태그 사이에 공백을 넣었다. 기존 countLines 통계는 이를 잡지 못해 tagged=0으로 저장했지만, 실제 canonical 파서는 허용하며 31개 모두 accepted였다. 따라서 위 표는 원문을 판독한 수치다. 원문을 고치지 않았다. canonical 검사에는 기존 캐시 프레임 문맥을 사용했으므로 영상 근거의 정밀 검증으로 해석하면 안 된다.

두 실행 모두 결과 저장과 임시 원격 파일 삭제까지 완료했다. SDK의 숫자 timeout 옵션이 성공 후에도 타이머를 남겨 프로세스 종료를 지연시키는 것을 발견해 native AbortSignal.timeout으로 변경했다. 이미 작업을 마친 두 프로세스는 타이머 대기 중 종료시켰다. 결과 원문·usage·로컬 asset은 보존했다. 변경 후 결정적 테스트를 재실행했다.

실제 원본의 특정 시각을 FFmpeg로 추출해 대조했지만 원음/TTS 전체 청취 및 시각장애인 평가는 하지 않았다. 영상 내 일부 정보 시점과 기존 추출 프레임의 지정 시각 사이 차이도 관찰되어, 시각 판단은 원본 MP4 해당 시각을 우선했다. 원인 조사는 이 실험에서 하지 않았다.

결론은 '영상 입력은 무효'가 아니라 '현재 저해상도 파일·정적 1fps 설정에서 기존 방식보다 품질이 좋아졌다는 근거가 없다'이다. 고해상도 또는 더 촘촘한 샘플링·agentic 처리의 효과는 아직 테스트하지 않았다. backend의 입력 방식을 변경하지 않는다.
