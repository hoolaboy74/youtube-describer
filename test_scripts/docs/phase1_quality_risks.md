# Phase 1 검증이 생성 품질에 미치는 영향

## 핵심 구분

1. 생성 전 promptPolicy: v2 정책 문구·태그·치환 여부 검사. -p 지정 시 우회한다. 의미적 품질 평가가 아니며 특정 표현을 요구하므로 좋은 대체 프롬프트도 거부할 수 있다.
2. 생성 후 canonicalOutput: 형식·태그·시간·길이·근거·언어·일부 중복 검사. backend는 accepted만 저장·TTS 처리한다.
3. 비교 스크립트: -p 여부와 무관하게 생성 후 canonical 검증 없이 모델 원문을 파일로 저장한다. 따라서 실험 원문과 실제 서비스 재생 대본은 다를 수 있다.

Phase 1은 현재 로컬 main에도 반영되어 있다. GSD 중단이 코드 제거를 뜻하지 않는다. 검증을 일괄 제거하거나 기준을 완화하는 것은 아직 승인받지 않았다.

## 한계·위험

- 길이 기본 제한 120자, 양수 정수 시간, 프레임/대사 근거 연결 때문에 유용한 문장도 탈락할 수 있다.
- 현재 시각 해설은 원음과 시간이 겹친다는 이유만으로 거부하지 않는다. 초기 Phase 1 완료 문서와 달라진 부분이다.
- 실제 이미지 속 행동이나 번역 의미의 정확성·완전성을 코드가 보장하지 않는다. 프레임 근거가 있다는 사실은 그 문장이 참이라는 증명이 아니다.
- 동일 문장·대사 중복 검사는 의미가 같은 모든 바꿔 쓰기를 탐지하지 못한다.
- normalizeText가 공백·문장부호·영문 대소문자를 정규화한 값을 실제 event.text에도 사용한다. 원문과 통과본의 표현 차이도 비교해야 한다.
- 통과한 번역의 실제 TTS 길이·겹침·seek/resume은 별도 검증 대상이다.

## 다음 개선 제안 — 아직 미구현

실험마다 raw / accepted / excluded+reasons를 나란히 저장한다. 원문 누락과 후처리 손실을 분리하고, 검증기 변경은 구체적인 오탐 사례별로 판단한다. 원본 모델 결과를 덮어쓰지 않는다.
